# Recovery runbook and verification gaps — 6 September 2026

This supplements `INCIDENT_RESPONSE.md`, `SUPPORT_PLAYBOOK.md` and the approved `PRODUCTION_OPERATIONS_PROFILE.json`. The profile records 99.5% availability, 15-minute SEV1 acknowledgement, 24-hour RPO and 4-hour RTO. These are objectives, not results of a fresh drill. Escalation contacts stay in the private production roster.

For every incident capture UTC time, release/config revision, request/job ID, affected operation and tenant scope. Never attach tokens, signed URLs, customer media or caption text to a public ticket. Preserve restricted evidence with a retention deadline. Do not retry financial or media side effects blindly.

| Failure / detection | Impact and automatic behavior | Manual recovery | Prevention / acceptance |
|---|---|---|---|
| Render timeout, RQ failed/stopped registry, job-age alarm | Polling reconciles dead jobs to failed; eligible retries are bounded; terminal states cannot be revived | Inspect job receipt, stored result and usage ledger before authorized replay; ensure old process is gone; use a new job ID for explicit replay | SIGKILL at render/upload/usage/terminal boundaries; prove no duplicate credit deduction and no stranded child process |
| Redis unavailable or lost data | Protected admission fails closed; status/queue coordination may be unavailable; Firestore mirrors do not recreate the RQ queue automatically | Pause admission, restore Redis according to operator policy, compare Firestore jobs, RQ registries, storage results and usage receipts; reconcile each uncertain job before replay | Managed persistence/failover, alerts and tested outbox/reconciliation; never flush Redis as a recovery shortcut |
| API crash during transcription | Client may see lost request; cached receipt/provider outcome can be uncertain; no durable transcription worker | Inspect provider/request history and cached result before retry; explain interrupted work to affected user | Durable transcription intent/outbox/result persistence remains open engineering work |
| Provider outage/timeout/cost spike | Existing bounded requests/retries can fail; some outcomes are ambiguous | Pause new paid-provider work, inspect reconciliation and budget, restore one test journey before reopening | Provider-specific retry classification, stable operation keys where supported and injected outage/load tests |
| Invalid media/scanner outage | Request rejected; production scanning configuration is required | Check scanner health/signature age and quarantine cleanup; never bypass scanning to clear backlog | Safe fixture tests plus real scanner outage, malicious/container and quarantine-access drills |
| Disk full or worker OOM | Render/upload fails; a killed worker may leave scratch files/descendants | Drain affected worker; confirm process ownership and inactive job before deleting job-specific scratch; provision capacity and replay safely | cgroup CPU/memory/PID limits, filesystem quota, worker-only scratch volume, age/ownership janitor; do not run broad recursive deletion |
| Payment duplicate / stale order / refund before capture | Payment receipts prevent repeated grant; older subscription event conflicts; missing refund receipt requests redelivery | Compare signed event, provider order/payment/refund state, user receipt and current entitlement; apply reviewed reconciliation with audit trail | Test real webhook retries/order permutations and Firestore contention; backfill legacy watermark from provider order creation time |
| Account deletion during active work | Durable deletion fence blocks new work/media, returns conflict while leases drain | Retry deletion after jobs finish/expire; verify user subtree, local/object media and Auth account cleanup; retain minimal fence until retention policy permits removal | Test delayed upload/payment/bootstrap callbacks and restore exclusion; never remove fence to repair a login |
| Release mismatch/readiness failure | New verifier rejects missing/mismatched component identity; draining workers are not ready | Pause rollout/admission, finish old work, deploy one compatible release or use coordinated rollback procedure | Required release gate, matching manifests and private worker checks; see `RELEASE_CANDIDATE.md` |

## Monitoring acceptance

Existing repository health, SLO, analytics and alert hooks are useful. They do not prove multi-region monitoring or successful alert delivery for this release. Provision independent DNS/HTTPS checks and an authenticated test-account upload → transcription → export → download journey, with a strict provider spend budget and automatic fixture deletion. Keep public status hosting independent of the app's primary failure domain.

Monitor error ratio/latency, queue depth/oldest age, worker heartbeat/draining/stale jobs, retry/failure rates, provider duration/429/5xx, webhook failures/reconciliation lag, credit conflicts, object cleanup failures, scanner health, disk/memory/PID pressure, auth/App Check denial trends and daily spend. The approved initial queue thresholds are warning depth 5 / age 5 minutes and critical depth 10 / age 15 minutes. Verify alert routing and on-call acknowledgement; no new external monitor or notification was created in this audit.

Structured API logs now identify service, environment and release with request ID. Public unexpected failures expose a generic message and correlation ID. Full caption style dumps were removed, but this is not proof every historical log/provider exception is redacted; inspect representative restricted logs before sign-off.

## Backup and restore procedure

1. Inventory authoritative data: Firestore accounts/entitlements, payment and usage ledgers, job metadata, deletion fences, private source/export objects where retention requires them, configuration/rules/index revisions and secret references. Browser-local draft captions are **not covered** by server backup. Redis queue persistence and Firestore snapshots are different recovery mechanisms.
2. Configure scheduled encrypted Firestore/object backups consistent with the approved 24-hour RPO. Scope operator access, backup location/residency, object lifecycle and payment-record retention explicitly. Verify scheduler success and alert on missed/old backups. Redis persistence must be private and protected; RQ payloads are trusted-code pickle data, never accept an untrusted Redis backup.
3. Restore a selected snapshot into isolated resources with outbound paid-provider work and customer notifications disabled. Restore rules/indexes and deploy the compatible artifact/config revision. Do not point production credentials or public DNS at the restore environment.
4. Reconcile snapshot time against provider payment/refund history and export-usage receipts. Overlay deletion fences and post-snapshot deletion records so restoration cannot resurrect deleted accounts/media. Compare sampled ledger totals and ownership, not just document counts. Retained backups must honor the documented deletion/retention policy.
5. Verify two-account isolation, login/bootstrap, draft recovery limitations, media integrity/checksums, caption/export correctness, payment duplicate handling, signed URL access/expiry and deletion. Reconcile queue state before replay; inspect jobs around the snapshot boundary and ensure old workers are stopped.
6. Record actual restore start/end time, last recoverable transaction time, recovered counts/checksums, exceptions and named approval. Compare measured RTO/RPO with objectives. Delete isolated drill resources according to the retention policy after evidence is retained.

**REQUIRES EXTERNAL VERIFICATION:** current backup schedules, restore credentials, actual data recovery, multi-region monitoring, alerts and container/process isolation. Earlier drill documents are historical evidence; no fresh restore or failover was performed here.
