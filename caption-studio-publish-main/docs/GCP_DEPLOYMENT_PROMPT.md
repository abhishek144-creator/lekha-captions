# Google Cloud zero-idle deployment prompt

Use this prompt for the next Lekha Captions Google Cloud deployment under the owner's chosen new account. This is a plan and implementation brief, **not authorization to deploy or create paid cloud resources**. The owner chose Google Cloud for low idle cost and explicitly does not want another 100-user load test. A different email does not change cloud prices or erase charges on the old billing account.

## Start with the current project record

Act as the implementation engineer and cost reviewer. Before changing any project file, read `AGENTS.md`, `CLAUDE.md`, and **all of `DEVELOPMENT_LOG.md`**, then inspect Git status and existing diffs. Before **every** cloud deployment or infrastructure apply, reread the current development log and this prompt; do not rely on a summary from an earlier session. Read `docs/ARCHITECTURE_GAP_VERIFICATION_2026-09-28.md`, `deploy/gcp/terraform/README.md`, and the current deployment configuration as historical evidence, then verify present code and live state separately. Preserve uncommitted work and customer data. Never print secrets.

The September billing incident involved two always-on API VMs, three always-on render VMs, provisioned Redis, load balancing, NAT, disks/IPs, and temporary load-test resources. Stopping application workers did not prove the VM groups or Redis stopped billing. Source defaults later changed toward zero minimums, but the last read-only inventory still found the five old VMs. The current Terraform still describes legacy VMs, Standard HA Redis, NAT, load balancing, and scheduled API calls. **Do not apply the existing configuration unchanged to a new project.** Treat the 2026-09-28 development-log incident entry as the cost and evidence baseline, not as proof of today's cloud state.

## Target architecture and implementation work

1. Keep the frontend static and preserve the marketing/dashboard domain split recorded in the development log. Put the API on Cloud Run with request-based billing, minimum instances **0**, a small explicit maximum, and measured CPU, memory, concurrency and timeout. It starts for requests; do not leave an API VM group or an always-on Cloud Run worker pool behind.
2. Keep uploads and completed exports in a private, lifecycle-managed Cloud Storage bucket. Use authenticated direct resumable uploads. Store the media in Cloud Storage; Cloud Tasks carries a small job reference, never the video bytes. Preserve quarantine, malware scanning, customer isolation, expiring signed downloads, and a data-retention policy. Estimate both stored GB-months and download/egress GB.
3. Use a durable, event-driven task path after upload or user action: enqueue scan, transcription, and export work in Cloud Tasks; have an authenticated dispatcher launch a Cloud Run Job for each accepted processing unit; end the job after completion. No Redis-polling worker, cron-driven dispatch loop, minute-by-minute queue metric call, or worker VM that runs merely because the dashboard is open. Separate job types and resource sizes where needed.
4. Design for Cloud Tasks redelivery and Cloud Run Job launch races. Use durable job records, transactional admission/outbox or an equivalent recovery mechanism, idempotency keys, bounded retries/backoff, dead-letter and stale-job recovery, cancellation, and safe completion. Ensure a worker crash cannot lose accepted work or charge a customer twice. For the first release, enforce **one total concurrent job execution** across types with a durable reservation; a one-task-per-execution setting alone does not prevent multiple executions from overlapping. Bound queue depth, per-user admission, task duration, job timeout, CPU/memory and total spend.
5. Remove Redis/RQ only after replacing **all** of its responsibilities: queue state, payment and webhook idempotency, credit deduction protection, rate limits, locks/admission, job status, and recovery/metrics. Use Firestore transactions or another justified durable design. The backend currently requires Redis in production; update that boot contract only when the replacement is implemented and tested. Do not weaken auth, payment, credit, rate-limit or media-scan controls to make the migration pass.
6. Inventory dependencies tied to the old billing project: Firebase Auth/App Check, Firestore records and indexes, media objects, secrets, images, domains/DNS, storage IAM, payment webhooks, and external AI providers. Plan a verified, data-preserving migration. Do not assume a new email automatically moves data or grants new free credits. Do not reopen or alter the old billing account as part of this new-project work without a separate owner decision.
7. Remove or avoid fixed-cost components in the **new** deployment: VM/MIG pools, Memorystore/Redis, VPC connector, Cloud NAT, external load balancer/forwarding rules, reserved IPs, persistent disks and unnecessary snapshots/images. If any is truly required, show its idle monthly cost and obtain the owner's explicit acceptance before creating it. A serverless service minimum of zero is insufficient if scheduled calls or other fixed services continue to run.

Translate the earlier AWS idea into Google services: SQS-like durable task delivery becomes Cloud Tasks, and short-lived Batch/Fargate-style processing becomes Cloud Run Jobs. The first pilot uses one total concurrent processing job. Previously discussed limits (API maximum 4; render 3; transcription 2; spot 1; GPU disabled; legacy API VM minimum 0) are ceilings to revisit only after measured demand and a priced review, not a reason to provision those pools now.

## Cost gate before any paid resource is created

Prepare a reviewable written estimate for the exact new account, billing account, project ID, region, SKUs, and current prices. List **every** retained resource and its idle monthly cost: Cloud Storage, Firestore, Firebase Hosting/Auth if applicable, Artifact Registry, Secret Manager, logging/monitoring, Cloud Tasks, DNS/domain, and any networking. Show per-upload, transcription, render, download/egress and third-party AI costs separately. State assumptions, tax/currency treatment, applicable free-tier limits, and the fact that free trial credit is temporary. Estimate no-traffic, small real usage, and a bounded worst-case month using actual plan/export assumptions rather than treating 100 users as 100 simultaneous exports.

Benchmark **one small, one typical, and one large real export** locally first. If cloud measurement is necessary, use only a small isolated pilot with one job at a time, a defined time limit, an estimated maximum cost, and a cleanup expiry. The owner does **not** authorize another 100-user or 250-user load test. Measure job seconds, vCPU, memory, media GB, downloads, paid transcription/provider calls, and cost per successful export. Reject unlimited or unmeasured scaling. Show the owner the cost estimate, resource inventory, spending controls, pilot limit, and a data-preserving shutdown/rollback procedure; obtain explicit approval before provisioning paid resources or launching the service.

Set several low budget thresholds and anomaly notifications, but state clearly that ordinary budget alerts do **not** stop charges. Apply low service maxima and quotas; define and test a shutdown switch that stops new job admission and compute while preserving queued jobs, payments and media. Do not use automatic billing closure as a substitute for orderly shutdown. Temporary resources must have an owner, expiry and verified deletion. The required target is **zero idle compute**, not a promise of a zero total bill: storage, Firestore above free quota, image storage, logs, egress and domains may still cost money.

## Verification and launch gates

- Run affected local backend, frontend, security, payment, upload and release checks. In isolated staging, perform a minimal end-to-end journey: login, direct upload, clean/rejected scan, transcription, edit, export, signed download and deletion/retention. Test duplicate tasks and webhooks, retries, worker failure, cancellation, stale-job recovery and credit/payment idempotency with disposable records.
- Prove a cold queue goes from zero workers to one job and back to zero. Confirm that no background polling, scheduler calls, VM group, Redis, NAT, load balancer or reserved IP remains in the new project's idle path. Observe an idle interval and inspect actual Cloud Run executions and billing; allow for billing-report delay. Source configuration and passing tests are not evidence of live idle cost.
- Before launch, inspect the saved infrastructure plan for unexpected paid resources and show the owner the exact project and account. Deploy only an approved immutable release, verify live minimum/maximum instance counts, job concurrency, quotas, task rates, resource inventory and budget notifications, then confirm the first daily SKU-level bill. If spend exceeds the agreed ceiling, stop new admission with the tested shutdown procedure and investigate before resuming.
- Do not claim the new deployment is live, cheap, or idle-free until the real resource inventory and observed bill support it. Record changed files, test evidence, resource inventory, cost measurements, approval, deployment state, and remaining risks in `DEVELOPMENT_LOG.md` after each phase.

Keep implementation and live deployment status distinct.
