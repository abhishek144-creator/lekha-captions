## Additional implementation

- Production `/api/process` commits an account-owned Firestore job and dispatch pointer in one transaction, returns 202, and replays durable results on subsequent requests. The browser polls pending jobs and cancels replaced client operations. Worker claims are transactional; duplicate delivery does not call the provider again.
- The dispatch loop recovers queued delivery after API/Redis interruption. A worker interrupted after claim is marked `unknown` after its bounded execution window. It is not automatically retried, including with a fresh browser request for the same source/settings. Result-persistence retries reuse the obtained result. OpenAI and Sarvam transport retries are disabled for transcription. This is controlled uncertainty, not an exactly-once guarantee from the provider.
- Cloud draft save/load endpoints use account ownership, a deletion fence, a 450 KB bound, optimistic revisions and five rotating recovery snapshots. Autosave retains the browser cache and saves to the account; conflicts remain visible instead of overwriting another device. A saved draft can be restored while source media exists or downloaded after source expiry. One current draft per account is supported; this is not a multi-project collaboration product.
- Account export includes the current cloud draft. Account deletion removes draft/job subtrees and waits for active transcription. Drafts contain source IDs instead of signed media URLs. Privacy pages and processing inventory describe these changes.
- Staging currently shares the Firebase project. Its transcription dispatch namespace is isolated, and scheduled global media cleanup/payment reconciliation are disabled there. A wholly independent staging Firebase project remains preferable.
